> **Original request:** "Found in beta UAT 2026-09-29. Reproduced 3/3 cold launches of the 0.86-beta built from `main`, and on the 0.84-beta.
>
> **Repro:** favorite at least one artist, quit, relaunch, wait 12s or more. Home shows "No upcoming tour stops" and "No shows on this date · 0 shows", even for Phish, which has 5 shows on 9/29. Un-starring and re-starring a favorite (which triggers `reloadDiscovery` with a new key) brings both sections back immediately.
>
> **Why it stays empty.** `OnThisDate.showsOnDate` (`CouchTourKit/OnThisDate.swift`) catches every per-artist error and returns `[]`. `OnThisDate.load` then caches that result under the day-plus-favorites key for the rest of the session, and `NextStop.load` does the same. So one failed or cancelled launch-time load blanks the shelves until the favorites change or the app restarts. The launch-time failure itself isn't pinned down yet; suspect the `HomeView` `.task` is cancelled or re-run during startup (sync kicks off at the same moment in `ThreePaneRootView`).
>
> **Fix:**
> - Don't cache empty results or results with errors.
> - Surface or retry failures instead of turning them into `[]`.
> - Find what fails at launch.
> - Check the Android side (`MainActivity.kt` `loadOnce`) for the same pattern."

## Problem / goal
The macOS Home screen's "Next Tour Stops" and "On This Date" sections show empty state ("No upcoming tour stops" / "No shows on this date") after a cold launch, even when data exists (e.g., Phish has shows on the current date). The root cause is that both `OnThisDate.load` and `NextStop.load` cache empty results from failed or cancelled launch-time network requests. Once cached, the empty result persists for the session until favorites change or the app restarts.

The same caching pattern exists on Android in `OnThisDate.kt` and `NextStop.kt`, where per-artist errors are caught and converted to empty lists, which are then cached.

## Plan
Files:
- `macos/Packages/CouchTourKit/Sources/CouchTourKit/OnThisDate.swift`
- `macos/Packages/CouchTourKit/Sources/CouchTourKit/NextStop.swift`
- `macos/CouchTour/HomeView.swift`

- `app/src/main/java/dev/mike/couchtour/NextStop.kt`
- `app/src/main/java/dev/mike/couchtour/MainActivity.kt`

Steps:
1. **macOS: Fix `OnThisDate.load` to not cache empty results**
   - Change the cache to only store non-empty results
   - Return the empty result without caching it when the fetch yields no shows
   - Add a `resetCache()` call path for explicit invalidation (already exists)

2. **macOS: Fix `NextStop.load` to not cache empty results**
   - Same pattern: only cache when `shows.isNotEmpty`
   - Return empty result without caching on failure

3. **macOS: Surface errors instead of swallowing them in `showsOnDate`**
   - Change `showsOnDate` to throw on total failure (all artists failed) rather than returning `[]`
   - Keep per-artist degradation (one artist failing doesn't fail the whole request)
   - Update `OnThisDate.load` to catch and log errors, not cache on error

4. **macOS: Surface errors in `currentTours` / `NextStop.load`**
   - Same pattern: throw on total failure, degrade per artist
   - Update `NextStop.load` to catch and log errors, not cache on error

5. **macOS: Update `HomeView.reloadDiscovery` to handle errors**
   - Show an error state in the UI instead of blank shelves when loads fail
   - Add retry button or auto-retry logic

6. **Android: Fix `OnThisDate.load` to not cache empty results**
   - Only cache when `shows.isNotEmpty()`
   - Return empty list without caching on failure

7. **Android: Fix `NextStop.load` to not cache empty results**
   - Only cache when `shows.isNotEmpty()`

8. **Android: Surface errors in `showsOnDate` and `currentTours`**
   - Throw on total failure (all artists failed)
   - Keep per-artist degradation

9. **Android: Update `MainActivity` UI to handle error state from `loadOnce`**
   - The `loadOnce` already returns `Result<T>?`; ensure error state shows retry option instead of blank

10. **Investigate launch-time task cancellation**
    - Check `ThreePaneRootView` sync startup interaction with `HomeView .task`
    - Ensure discovery loads aren't cancelled by sync initialization

Test: what proves it
- Cold launch with favorites → both sections populate within 12s (not blank)
- Network failure at launch → sections show retry/error state, not blank cached empty
- Toggle favorite off/on → sections refresh correctly (cache invalidation works)
- Unit tests: `OnThisDateTests.testOnThisDateCacheInvalidation` and `NextStopTests.testNextStopCacheInvalidation` should verify empty results aren't cached
- Android unit tests: `OnThisDateTest` and `NextStopTest` cache tests should verify same

## Context
- The issue was found in beta UAT (0.86-beta and 0.84-beta)
- The problem affects both macOS and Android platforms
- The caching is in-memory only (process death clears it)
- Un-starring/re-starring a favorite works because it changes the cache key
- Related to D162 (daily cache for discovery rows) and D164 (Next Stop caching)

## Out of scope
- Persistent disk caching for discovery rows (current in-memory cache is intentional per D162)
- Offline support (explicitly not planned per README)
- Changing the per-artist degradation strategy (it's correct: one artist failing shouldn't fail all)
- The `loadOnce` composable pattern on Android (it correctly preserves error state; only the data layer caching needs fix)
